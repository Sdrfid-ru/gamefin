# Работа с кодом

Начните с [README](README.md), [карты кода](docs/code-map.md) и [архитектуры](docs/architecture.md).
Текущая Android-игра работает локально; сервер в `backend/` развивается отдельно.

## Изменения

1. Создайте ветку от `main`, например `git switch -c feature/new-task`.
2. Внесите одно связное изменение. Правила денег находятся в `core/domain`, запись прогресса —
   в `app/data` и `GameViewModel`, представление — в `app/ui`.
3. Запустите подходящие проверки и просмотрите `git diff` перед коммитом.
4. В описании изменения укажите поведение до и после, выполненные проверки и известные ограничения.

Комментарии в коде поясняют причины ограничений. Если меняется правило, обновляйте комментарий
рядом с ним и соответствующее описание в `docs/`.

## Проверки

Форматирование и его проверку запускайте последовательно: Gradle настроен на параллельные задачи.

```sh
./gradlew formatKotlin
./gradlew checkKotlinFormat
./gradlew :core:domain:test :app:testDebugUnitTest :backend:test
./gradlew :app:lintDebug :app:assembleDebug
```

Для изменения экранов, восстановления состояния и Android-хранилища также нужны проверки на
эмуляторе или устройстве:

```sh
./gradlew :app:connectedDebugAndroidTest
```

Не переиспользуйте ID заданий и вариантов внешности: они хранятся в профиле. Изменяя сохраняемые
поля, обновляйте `ScenarioCodec` и проверки чтения/записи. Для нового задания существующего типа
используйте [каталог контента](docs/content-model.md).

## Состав репозитория

В Git входят исходники, Gradle Wrapper (включая JAR), ресурсы игры, лицензии ресурсов, тесты,
документация и её иллюстрации. APK, локальные презентации в `output/`, кэши, SDK, дампы,
настройки IDE, `.env` и ключи подписи исключены. Исключённые файлы остаются на диске.

Значения локальных переменных задавайте в `.env`, используя `.env.example` как шаблон.
Workflow проверки запускается на pull request и push в `main`. Workflow по тегу `v*` сохраняет
debug APK как артефакт GitHub Actions; подпись релизным ключом и публикация в магазин не настроены.
